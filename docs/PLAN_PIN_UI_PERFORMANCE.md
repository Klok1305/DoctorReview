# План: единые PIN, отзывчивые отчёты и согласованный интерфейс

Обновлено: **2026-10-10**. Статус: **PIN и ускорение включены в запущенный релиз 3.1.3; онлайн UI-проход выполнен локально, полный Admin и реальные устройства остаются**. Изменения и замеры быстродействия — [УСКОРЕНИЕ_ОТЧЁТОВ.md](УСКОРЕНИЕ_ОТЧЁТОВ.md). Релиз 3.1.3 запущен по просьбе пользователя; серверный деплой ещё не выполнен.

Запрос пользователя: подготовить план трёх работ для двух независимых Admin и онлайн-КлинВекта. Разработчик публикует обновления; сотрудник, работающий с клиникой, готовит отчёты и комментарии. Дополнение пользователя: считать отчёт выбранного врача по требованию и выполнять тяжёлые вычисления вне потока окна.

## Что установлено по текущему коду

- В [`database.cjs`](../desktop/services/database.cjs) `viewerAccessSnapshot()` выдаёт случайный PIN каждому врачу, для которого в этой SQLite ещё нет доступа. Независимые базы могут выдать разные PIN одному врачу. PIN врача хранится строкой, вместе с проверочным хешем, солью и локальной версией; администраторский PIN хранится только как проверочный хеш.
- [`exportViewerPinsTable()`](../build/app-ui.js) выгружает ФИО/PIN в Excel. Теперь [`pin-transfer-ui.js`](../build/pin-transfer-ui.js) и [`pin-transfer-service.cjs`](../desktop/services/pin-transfer-service.cjs) добавляют защищённый перенос, общий набор/ревизию и обновление только PIN онлайн. Полная JSON-копия по-прежнему восстанавливает также рабочую базу и служебные таблицы.
- Онлайн получает существующие проверочные хеши PIN из опубликованного Admin. Это снимок на момент выгрузки, а не автоматическая связь двух установок. [`cloudAccountsFromViewer()`](../desktop/services/cloud-publication-service.cjs) уже использует существующие хеши без открытых PIN.
- [`switchTab()` и `renderAll()`](../build/app-ui.js) строят активную вкладку. До ускорения `renderDoctor()` синхронно создавал подробности, годовую историю и все графики выбранного врача; теперь расчёты подготовлены worker, а графики создаются при просмотре; `doctorMetricDynamics()` многократно запрашивает историю этого врача. Сводки отделений/специализаций вычисляют показатели всего включённого состава и годовые агрегаты.
- Расчётные LRU-кэши и выборочная инвалидация уже реализованы в [`app-metrics.js`](../build/app-metrics.js), а импорт, основные записи SQLite и упаковка — в workers. Этапы A04/A08 не начинать заново. Пока не измерены время конкретного зависания, вкладка и вклад вычислений, DOM, таблиц и графиков в эту задержку.
- Визуальные правки из предыдущей задачи проверены локально, включены в запущенный релиз 3.1.3; серверный деплой ещё не выполнен.

## 1. Перенос и синхронизация PIN

1. За основу предложить набор из Admin сотрудника, который уже сообщает PIN врачам. Перед первым переносом подтвердить источник, чтобы сохранить уже выданные клинике коды. После этого менять общий набор в одном ответственном Admin и распространять новую ревизию.
2. В настройках добавить «Экспорт PIN» и «Импорт PIN». Использовать отдельный защищённый паролем файл с доступами и необходимыми сведениями для сопоставления врачей. Отчёты, пациенты и комментарии в такой файл не включаются. Прежняя Excel-выгрузка сохраняется.
3. Ввести идентификатор общего набора и ревизию. Отображать их в обоих Admin и онлайн; локальные `pinVersion` сейчас не являются общей версией между независимыми базами. Старый или посторонний набор не должен незаметно отменять более новую синхронизацию.
4. Перед импортом показывать сравнение: совпадения, изменяемые PIN, отсутствующие врачи, конфликтующие привязки и дубликаты. Проверять идентификатор врача вместе с его карточкой; при разных ID предлагать сопоставление по ФИО/специализации. Неоднозначное сопоставление разрешает пользователь. Импорт не создаёт выдуманные карточки врачей.
5. Сохранять ведущие нули. Администраторский PIN переносить отдельно по выбору пользователя через существующий проверочный хеш; открытый код из хеша не восстанавливается. Флаги доступа и назначения заведующих сохранять, если пользователь отдельно не выбрал их перенос.
6. Применять согласованный набор одной транзакцией после резервного сохранения прежних доступов. Поддержать обмен PIN между врачами, проверить конфликты с врачами вне импортируемого состава. При ошибке сохранять весь прежний набор; повторный импорт той же ревизии не должен менять коды или повышать версии.
7. Для онлайн предусмотреть отдельное обновление PIN из синхронизированного Admin с прежними серверными проверками прав. Обновлять доступы атомарно, сохраняя опубликованные страницы, комментарии и роли. Онлайн получает только проверочные хеши и метаданные набора. При изменении PIN прежние сессии отзываются; обычная публикация отчётов также несёт актуальную ревизию и не должна возвращать старый набор.
8. Проверить сценарий двух отдельных SQLite с разными кодами: источник → второй Admin → онлайн; вход тем же PIN во всех новых публикациях. Проверить `0123`, несовпадающие ID, однофамильцев, дубликаты, обмен кодами, неправильный пароль файла, старую ревизию, повтор, отказ в середине операции и администраторский PIN. Сверить, что данные отчётов, комментарии и права не изменились. Старые автономные HTML/ZIP имеют собственный снимок доступов и для обновления PIN требуют новой публикации.

Критерий готовности: один врач использует один согласованный PIN; оба Admin и онлайн показывают один набор/ревизию, а перенос не заменяет рабочие отчёты и комментарии.

## 2. Быстродействие: выбранный врач и вычисления по требованию

1. Зафиксировать воспроизведение: какая вкладка зависает, выбранный врач/период, число врачей и месяцев. На копии базы при её предоставлении измерить первое и повторное открытие врача, отделения и специализации. Отдельно измерить расчёт, подготовку истории, сборку HTML/DOM, подробных таблиц и графиков; записать длинные задачи, память и задержку реакции окна. Первые проверки выполнять на синтетическом наборе, затем сверить на копии реального объёма.
2. Сначала показывать переключатели, заголовок и состояние загрузки, затем основные показатели выбранного врача за текущий период. Рассчитывать историю, тяжёлые подробности и графики следующими задачами по мере потребности: раскрытие раздела или появление графика на экране. Само наличие свёрнутой таблицы не должно заставлять строить все её строки.
3. Переиспользовать существующие расчётные кэши. При необходимости добавить ограниченный кэш модели/подготовленного представления с ключом врача, периода, окон анализа и ревизий данных/нормативов. Изменения комментария не должны запускать пересчёт всех числовых показателей.
4. Вынести подтверждённые замерами тяжёлые расчёты в отдельный worker. Отделить расчёт от DOM, изменяемого `UI` и глобального состояния, передавать согласованный снимок необходимых данных и нормативов. Учесть стоимость передачи и память; не копировать всю базу для каждой карточки. Асинхронная функция или `setTimeout` сами по себе оставляют вычисления в потоке окна, поэтому дробление и worker проверять измерениями.
5. Использовать ограниченную очередь с приоритетом текущего экрана. При выборе другого врача, месяца или уходе с вкладки отменять ненужную подготовку, а запоздавшие результаты отбрасывать по идентификатору запроса и ревизии. Фоновую подготовку запускать только без ущерба активному запросу.
6. Отдельно оптимизировать сводки: им нужны данные всех включённых врачей. Готовить согласованный агрегат в фоне, показывать прогресс и не заменять полный результат частичным без обозначения. Ограничить первоначальный DOM больших таблиц и число одновременно строящихся графиков.
7. Разделить экранный просмотр одного врача и пакетный экспорт. Экспорт всех врачей остаётся отдельной фоновой операцией с прогрессом/отменой и единым снимком данных. Отложенный экранный рендер не должен приводить к пустым разделам PDF, Viewer или онлайн-публикации.
8. Сравнить числовые результаты с прежними для полного/неполного набора, пропущенного месяца и смены нормативов. Проверить быстрое переключение врачей и изменение данных во время расчёта. Сравнить холодные/повторные открытия, максимальную блокировку окна и память до/после на одинаковом наборе.

Критерий готовности: окно реагирует во время подготовки отчёта, актуальный выбранный врач получает приоритет, повторные открытия используют кэш, а показатели и экспорт совпадают с эталоном. Предварительная цель для реакции переключателя/индикатора — до 100 мс; бюджет полного отчёта уточнить после исходных замеров.

## 3. Интерфейс Admin и онлайн на ПК/телефоне

1. Сначала составить список экранов/состояний и выявленных дефектов; окончательную проверку выполнить после изменения загрузки отчётов. Включить «Данные», «Настройки», «Врач», специализации, отделения, онлайн-вход, публикацию, комментарии, диалоги, ошибки и загрузку. Проверить новые экраны переноса PIN и длинные таблицы/ФИО.
2. Матрица: Admin при 1040, 1280, 1440 и 1920 px, масштаб Windows 100/125/150%; онлайн на ПК и телефоне 360/390/430 px, горизонтальный экран и iframe Битрикса. Проверить роли врача, заведующих специализацией/отделением и администратора.
3. Проверять выход элементов за экран, перенос заголовков и сумм, размеры кнопок/полей, локальную прокрутку таблиц, открытие разделов, читаемость графиков и сообщений загрузки. На телефоне учитывать экранную клавиатуру. Сохранять снимки дефектов и исправленного состояния.
4. Общие правила оформления выносить в общие модули/стили, где это соответствует устройству обоих продуктов. Каждую затронутую визуальную правку проверять в Admin и онлайн, включая прежние HTML-публикации. Доски почёта не возвращать.
5. Выполнить Electron smoke на обычном/узком окне, WebKit на узком/горизонтальном iPhone и iframe; провести визуальную проверку снимков. При затронутой печати проверить PDF. Физический телефон и реальный портал — заключительная ручная проверка вместе с пользователем; эмуляция её не заменяет.

Критерий готовности: нет выхода всей страницы за экран, длинные таблицы имеют свою прокрутку, основные действия доступны в каждом состоянии и роли, а Admin и онлайн выглядят согласованно.

## Порядок выполнения и точка продолжения

1. Согласовать источник PIN и снять исходные замеры/снимки.
2. Реализовать и проверить перенос PIN, общий набор и его обновление онлайн.
3. Ускорить подготовку отчётов по измерениям, начиная с выбранного врача и тяжёлых подробностей.
4. Завершить UI-проход на итоговом рендере, включая загрузку/отмену и миграцию PIN.
5. Выполнить необходимые регрессии и audit; подготовить согласованный комплект Admin/онлайн. Запуск выпуска и деплой выполнять по отдельной просьбе.
