# Обзор архитектуры: скорость, расчёты и мобильная версия

Дата: **2026-09-12**. Версия: **2.6.13**. Проверены исходники Admin, расчётов, импорта, SQLite, локальных сервисов, PDF, обоих Viewer, PWA, мобильного сервера и сборки. Аудит безопасности не проводился. Шифрование рассматривается только как вычислительная нагрузка.

## Основной вывод

Текущая архитектура пригодна для локального Admin и мобильного просмотра готовых отчётов. Её главный предел — работа с целой базой и тяжёлыми операциями в потоках интерфейса и обслуживания запросов. Для полноценного мобильного Admin расчёты нужно отделить от глобального состояния, HTML и Electron.

Есть и проблемы правильности, которые нужно исправлять раньше ускорения: импорт может считаться успешным без сохранённых данных, сводный средний чек может смешивать выручку всех врачей с пациентами только части врачей, а мобильная версия теряет признак предварительного балла.

Ниже «воспроизведено» означает проверку небольшим синтетическим сценарием. «Риск по коду» означает установленный механизм без измерения реальной нагрузки клиники. Тесты не доказывают отсутствие всех ошибок формул.

## 1. Импорт может зафиксировать успех без данных

**Воспроизведено.** В `handleFilesBatch()` сначала вызывается `recordImport()`, который устанавливает `source_files.successful = 1`, и только затем `saveLocal()`. Ошибка сохранения превращается в `false`, но итоговое `await lastSave` это значение не проверяет. Пакет завершается с прежними счётчиками успеха.

Сценарий: один синтетический XLSX; результат парсера заменён на успешный; настоящий сервис SQLite записывает историю импорта; `saveDatabase()` принудительно возвращает ошибку. Получено: `loaded: 1`, `errors: 0`, `sourceSuccessful: true`, `loadSnapshot(): null`. При следующем обычном импорте такой SHA-256 будет пропущен как уже обработанный. Без отказа записи остаётся окно между двумя отдельными операциями, в котором процесс может завершиться.

**Исправление:** одна транзакционная команда сохранения импортированного блока и его происхождения. Успех источника выставлять только при успешном commit аналитики; возврат `false` должен прерывать успешное завершение пакета. Для больших импортов нужны небольшие атомарные порции, а не транзакция на весь каталог.

Код: [порядок импорта](../build/app-parsers.js), функции `handleFilesBatch`, `ensureDesktopFileSource`; [очередь сохранения](../build/app-core.js), `flushDesktopSaveQueue`; [история источников](../desktop/services/database.cjs), `recordImport`, `hasSuccessfulSource`.

## 2. Неполные данные искажают сводный средний чек

**Воспроизведено.** `aggregateDeptMonth()` складывает выручку всех доступных врачей. Число пациентов получает из месячных клиентских баз тех врачей, для которых они есть. Отсутствие базы одного врача не блокирует деление.

Сценарий: два врача, у каждого выручка 1000; месячная клиентская база есть только у первого и содержит одного пациента. Сводка показывает выручку 2000, одного пациента и средний чек 2000. По имеющимся данным средний чек всего отделения неизвестен; для полного поднабора он равен 1000. Аналогичный принцип независимого суммирования числителей и знаменателей используется для загрузки расписания; этот путь нужно проверить отдельно.

**Исправление:** для каждого отношения явно определять одинаковую совокупность врачей в числителе и знаменателе. Либо показывать показатель только при полной сопоставимой базе, либо показывать частичный показатель с количеством включённых врачей. Не превращать отсутствующие выгрузки в нули.

Дополнительная методическая граница: `uniqueClientBase()` объединяет группы одного пациента у разных врачей через объединение множеств. Поэтому пациент может быть активным у одного и потерянным у другого, а в сводке войти в обе группы. Это допустимо как «отношения пациент–врач», но не как непересекающиеся сегменты единой базы отделения. Для второго определения нужна повторная классификация объединённой записи по согласованным нормативам. Слияние по имени при отсутствии ID тоже требует явно описанной политики совпадений.

Код: [агрегаты отделения](../build/app-metrics.js), `aggregateDeptMonth`, `uniqueClientBase`, `sum`.

## 3. Сохранение растёт вместе со всей историей

**Измерено.** `saveLocal()` синхронно сериализует весь `DB`. Main получает строку через IPC, разбирает JSON; `saveSnapshot()` снова сериализует и хэширует настройки, каждого врача и каждый месяц. SQL сравнивает хэши и не переписывает неизменившиеся строки, но стоимость подготовки уже понесена. `loadSnapshot()` также читает все месяцы сразу.

При импорте это происходит после каждого файла. Если каждый файл добавляет одинаковый объём данных, суммарная сериализация растёт примерно как `1 + 2 + … + F`, то есть квадратично относительно числа файлов в такой пачке. Очередь сохранения объединяет ожидающие снимки, но не отменяет уже выполненный `JSON.stringify()` для каждого файла.

На синтетической базе 27,9 МБ только сериализация занимала 116–143 мс; сохранение снимка после изменения одной заметки и повторные сохранения того же снимка — 208–228 мс. В эти числа не включены IPC и разбор JSON в main. В `database:save` есть предел длины строки 200 × 1024 × 1024 символов: это потолок для всей истории, а не для одной новой выгрузки.

**Исправление:** хранить ревизии и изменённые блоки; передавать по IPC только дельту месяца/врача/настройки. Комментарии и интерфейсные предпочтения не должны пересохранять все клинические выгрузки. Следующий шаг — выборочная загрузка истории. Немедленная полная замена SQLite не нужна: сначала можно сохранить существующие JSON-строки и добавить точечные команды поверх них.

Код: [saveLocal](../build/app-core.js), [database:save](../desktop/main.cjs), [saveSnapshot/loadSnapshot](../desktop/services/database.cjs).

## 4. Кэш помогает, но дорого пересчитывать и хранить его содержимое

**Подтверждено кодом и замерами.** `computeMetrics()` имеет кэш по врачу и месяцу; повторные обращения очень быстрые. Но любой `saveLocal()`, включая смену настройки показа баллов, сбрасывает весь кэш.

Внутри одного `computeMetricsRaw()` клиентская база проходит через `kbSummary()` отдельно для 1, 12 и 36 месяцев, затем ещё раз для доступных окон и ещё раз для курсового окна. Исторический средний чек повторно вызывает сводки выработки и месячной базы. `kbSummary()` нормализует пациентов, создаёт новые строки и массивы, сортирует базу для ядра выручки. Для одного скалярного среднего чека выполняется значительно больше работы, чем нужно.

`adminClientBaseSummary()` дополнительно строит старую сводку, а потом новое разбиение с копиями строк. Его вызывают и годовая таблица, и график. У `aggregateDeptMonth()` нет собственного кэша: даже при готовых персональных метриках заново объединяются пациентские списки нескольких окон. Кэш персональных метрик не ограничен по размеру и хранит подробные `clientRows`, включая повторные представления одного окна; это риск роста памяти, её пик в этом обзоре не измерялся.

**Исправление:** отдельные кэши исходных агрегатов по `(doctorId, month, window, dataRevision, profileRevision)`; отдельный расчёт скалярных сумм без пациентских строк; детали строить по запросу. Сбрасывать только затронутые ключи. Кэш отделений должен учитывать состав врачей, фильтр и ревизии. После этого вынести тяжёлые расчёты в worker, сохранив одно место определения формул.

Код: [расчётный модуль](../build/app-metrics.js), `computeMetricsRaw`, `kbSummary`, `adminClientBaseSummary`, `aggregateDeptMonth`; [годовые представления](../build/app-ui.js), `adminDoctorDynamics`, `adminClientBaseSeries`.

## 5. На телефоне теряется признак предварительного балла

**Воспроизведено.** Ядро вычисляет `coveragePct`, `rankEligible`, `preliminary`, список `missing`. Admin использует полноту для трактовки оценки. `mobilePublicationScore()` берёт только число; `buildMobilePublicationPeriod()` присваивает обычный текст оценки и не передаёт статус полноты.

Синтетический пример: полнота 47,4%, `rankEligible: false`, индекс 23,1. В мобильную публикацию ушли индекс 23 и оценка «Требуется внимание», без поля полноты. Получатель не может отличить недостаток выгрузок от плохого результата. Значение 23,1 не является само по себе ошибкой; проблема — потерянный контекст.

Также мобильные карточки некоторых целей используют `Number(benchmark)`: пустая строка или `null` превращаются в ноль, хотя расчётное ядро трактует пустую цель как отсутствие оценивания. Это отдельное расхождение контракта отображения.

**Исправление:** добавить обратно совместимые поля полноты, предварительности, источников и причин отсутствия. Использовать единые определения «цель задана» и форматирования оценки. Проверять одну и ту же модель отчёта в Admin, Viewer и PWA.

Код: [мобильный построитель](../build/app-ui.js), `mobilePublicationScore`, `buildMobilePublicationPeriod`; [схема публикации](../desktop/services/mobile-publication-service.cjs); [scores](../build/app-metrics.js).

## 6. Одно название В4 скрывает разные определения

**Подтверждено кодом.** Admin показывает новое разбиение `partitionClientBase()` на четыре непересекающиеся группы и только по точной базе за 36 месяцев. Viewer заменяет этот блок старым представлением из `kbSummary()`. Мобильный построитель также использует прежние группы, окна 12/24/36 и `selectedClientBaseSummary()`.

Кроме различий между клиентами, внутри Admin новый В4 и годовая таблица используют новое разбиение, а часть KPI и балл В4 — прежние определения. Изменение `clientBasePartition` поэтому меняет диаграмму, но не обязано менять балл. Это сохранённая совместимость, а не повод незаметно заменить формулы.

**Исправление:** согласовать, должны ли все потребители показывать одинаковые сегменты. Разделить идентификаторы показателей по смыслу, включить в публикацию версию методики и период источника. Строить содержательную модель отчёта один раз и адаптировать её к разным экранам. Старые опубликованные пакеты должны оставаться читаемыми.

В текущем изменении исправлен только вид настроек: четыре строки с визитами и сроком, общие границы синхронизируются. Формулы и определения публикаций не менялись.

Код: [partitionClientBase/kbSummary](../build/app-metrics.js), [viewerClientBaseHtml, composeViewerDashboardHtml, mobilePublicationClientWindows](../build/app-ui.js).

## 7. Полностью отсутствующий месяц исчезает из части динамики

**Воспроизведено.** `buildDynamics()` выбирает последние существующие ключи `DB.months`, а предыдущим считает соседний отображаемый ключ. Если в базе есть январь и март, но вообще нет февраля, сравнение марта будет с январём.

Синтетический пример: выручка января 1000, марта 2000. Получены колонки `2025-01`, `2025-03` и изменение +100%. История карточки через `doctorMetricDynamics()` ищет именно февраль и в этом случае должна показывать отсутствие базы сравнения. Если февраль существует в общей базе, но отсутствует только у конкретного врача, поведение иное: пустой месяц сохраняется. Поэтому ошибка проявляется не на всех наборах данных.

**Исправление:** единый календарный генератор месяцев и явно названные типы сравнения: предыдущий календарный месяц, предыдущий доступный отчёт, среднее за конкретный диапазон. Пропуск месяца должен вести к одинаковому результату в карточках и динамике. Отдельно согласовать среднее чеков по месяцам и взвешенный чек периода: сейчас это разные математические показатели.

Код: [buildDynamics/computeDoctorDynamics](../build/app-metrics.js), [doctorMetricDynamics/mobilePublicationDynamics](../build/app-ui.js).

## 8. Тяжёлые операции блокируют обработку событий

**Подтверждено кодом.** В renderer синхронны чтение XLSX библиотекой, перевод листа в строки и расчёты. ZIP раскрывается в массив файлов до начала основной обработки. В `exportAllMobilePublications()` нет уступки управлению между врачами. В main синхронны SQLite, часть файловых операций, хэширование и подготовка шифрованных пакетов. Ключевое слово `async` у IPC-обработчика само по себе не делает эти операции фоновыми.

На мобильном сервере `pinKey()` вызывает `scryptSync`; загрузка завершается полным чтением, разбором, валидацией и сериализацией пакета. Запись порциями по 512 КиБ ограничивает отдельный HTTP-запрос, но не пиковую обработку финального файла. Допускается пакет до 100 МБ. При проверке входа и обновлении пакета могут задерживаться и другие запросы этого процесса.

На локальном стенде один вход с чтением небольшого отчёта занимал 59–63 мс, создание пакета для 10 получателей — 607–623 мс. Это не нагрузочный тест Black Hole и не оценка его реальной пропускной способности.

**Исправление:** один worker-владелец записи SQLite с очередью, workers для парсинга и построения пакетов, асинхронное выведение ключа с ограниченной конкуренцией на сервере. Не запускать тяжёлую операцию сразу в сотне потоков. Добавить прогресс, отмену и измерение задержки цикла событий. Параметры шифрования ради скорости не ослаблять.

Код: [processFile/expandZips](../build/app-parsers.js), [локальные файлы](../desktop/services/file-service.cjs), [pinKey/createMobilePublicationBundle](../desktop/services/mobile-publication-service.cjs), [мобильный сервер](../mobile-server/server.cjs).

## 9. Экспорт Viewer связан с экраном и размножает содержимое

**Подтверждено кодом.** `composeViewerDashboardHtml()` получает DOM через `pdfTargetSource()`, клонирует экран и затем заменяет некоторые блоки. Экспорт меняет общий `UI`, а потом восстанавливает его. Это усложняет фоновую генерацию, тестирование и гарантированно единый снимок при длительной операции.

Сводный HTML отделения кэшируется при подготовке, но добавляется в `pages` для каждого врача. ZIP повторно шифрует каждую разрешённую страницу для каждого получателя; заведующий получает ещё набор подчинённых. Автономный HTML хранит отдельные наборы получателей и полный каталог администратора. У ZIP выведение ключа выполняется на каждую страницу. Пределы размера проверяются уже после формирования результата. Мобильный пакет v2 уже лучше в этом отношении: отчёт хранится один раз, отдельно выдаются права на его ключ.

У установленного Viewer импорт создаёт новые каталоги `releases`; очистки старых выпусков в `storage-service.cjs` нет. Записи каталогов атомарны по файлу, но применение всего пакета состоит из нескольких замен. Это риск расхода диска и частично применённого обновления при отказе записи, а не подтверждённое повреждение пользовательской установки.

**Исправление:** строить неизменяемую модель отчёта из конкретной ревизии данных; отдельно рендерить её в HTML, PDF и JSON. Использовать общие объекты страниц с выдачей ключей, ограничивать и оценивать размер до массовой генерации. Для Viewer добавить согласованную смену поколения каталога и политику удержания старых файлов с сохранением совместимости.

PDF через Chromium `printToPDF()` уже является разумной отдельной границей. Возвращаться к сплошной картинке не требуется. Пакетная печать создаёт скрытое окно на каждый вызов; необходимость переиспользования окна следует решать после замера реального PDF-пакета.

Код: [экспорт и композиция](../build/app-ui.js), [упаковка Viewer](../desktop/services/viewer-package-service.cjs), [хранилище Viewer](../viewer/storage-service.cjs), [печать PDF](../desktop/main.cjs).

## 10. Что мешает полноценному мобильному переносу

PWA уже получает готовый компактный отчёт, а не всю SQLite. Это полезное разделение: на измеренном наборе рост исходной базы с 7,3 до 27,9 МБ почти не изменил размер мобильного пакета — около 2,1 МБ. Но сервер не умеет пересчитывать метрики: новая информация появляется только после экспорта и загрузки общего пакета из Admin.

| Мобильная задача | Текущее состояние | Что требуется |
|---|---|---|
| Чтение личных отчётов и отчётов подчинённых | Реализовано | Исправить полноту/паритет показателей, измерить реальные телефоны |
| Чтение после перезапуска без сети | Кэшируется оболочка; рабочий отчёт живёт в памяти | Отдельный продуктовый сценарий сохранения и обновления отчётов |
| Возобновление загрузки пакета при обрыве | Последовательные порции; нет повторов и восстановления позиции в клиенте | Идемпотентные порции, resume, таймауты и понятный повтор |
| Импорт 1С и настройка расчётов с телефона | Отсутствует | Общий расчётный модуль, хранилище, задачи импорта на сервере/worker |
| Совместное редактирование нескольких администраторов | Общий mutable `DB` и локальный SQLite-снимок | Ревизии, команды изменения, политика конфликтов и серверный владелец записи |

`apiRequest()` не задаёт таймаут или сигнал отмены; при зависшем запросе пользователь может долго ждать заблокированную кнопку. Сервер отправляет публикацию сразу со всеми периодами; отдельного запроса месяца нет, JSON-ответы не сжимаются этим сервером. Клиент хранит несколько заранее отформатированных строк вместо типизированных значений и единиц; для изменения локали, пересчёта или единых сравнений это слабый контракт. Числовые ряды графиков уже передаются отдельно — их подход можно расширить на показатели.

**Рекомендация для этого репозитория:** сохранить PWA как клиент просмотра и сначала выделить общее расчётное ядро и модель отчёта. Не начинать перенос с копирования 7000-строчного `app-ui.js` в телефонный интерфейс или полного переписывания всех клиентов.

Код: [PWA](../mobile-pilot/app.js), [service worker](../mobile-pilot/service-worker.js), [API](../mobile-server/server.cjs), [построение публикаций](../build/app-ui.js).

## 11. Предел сессий приводит к массовому выходу

**Воспроизведено через локальный HTTP-сервер.** При `state.sessions.size >= 2000` обработчик входа вызывает `cleanState(Date.now() + SESSION_TTL_MS)`. Все обычные действующие сессии истекают раньше этого искусственного времени и удаляются. Новая сессия остаётся единственной. Та же очистка может удалить текущие незавершённые загрузки.

Сценарий: в состояние помещены 2000 синтетических ещё действующих сессий, затем выполнен один настоящий PIN-вход. HTTP 200, число сессий после запроса — 1. Для небольшой клиники предел может быть далёким, но поведение при достижении лимита ошибочно. Сессии также хранятся только в памяти одного процесса: его перезапуск требует повторного входа, а несколько экземпляров сервера не имеют общего состояния.

**Исправление:** чистить по настоящему времени; при достижении лимита удалять ограниченное количество старейших сессий или отклонять новый вход с понятной причиной. Общее хранилище требуется только при реальной необходимости нескольких экземпляров.

Код: [createMobileServer, cleanState, /api/login](../mobile-server/server.cjs).

## 12. Что подтверждают и чего не подтверждают проверки

Пройдены **150 Node-тестов**, сборка renderer и Electron smoke. Дополненная smoke-проверка проверяет четыре строки настроек, по два числовых поля, изменение через реальные события `input`, связанные границы, режим любого числа визитов, сохранение и отказ на неверном пороге. Алгоритм разбиения дополнительно покрыт существующими тестами границ и сохранения.

Первый запуск `pnpm test` попытался автоматически пересобрать окружение зависимостей и остановился без TTY. Сначала тот же набор был запущен непосредственно через `node --test tests/*.test.cjs`, после UI-правок — через `pnpm test` с отключённой автоматической перепроверкой зависимостей (`pnpm_config_verify_deps_before_run=false`). Пакеты и lockfile не изменялись. Electron в ограниченной среде не смог запустить renderer; тот же smoke успешно прошёл вне неё на синтетической базе.

В текущем CI есть Node-тесты; smoke/PDF не выполняются ни обычным, ни релизным workflow. Много проверок UI проверяют присутствие строк в исходниках. Это полезные инварианты, но они не заменяют проверку показанного значения. В тестах renderer функции также извлекаются из `app-ui.js` строковыми срезами — дополнительный признак слабых границ модулей.

Нужны регрессионные проверки перечисленных отказов и один общий набор эталонных результатов для Admin/Viewer/PWA, включая неполные базы, отсутствующие месяцы и смену нормативов. Для скорости — воспроизводимый нагрузочный сценарий с лимитами времени, памяти и задержек интерфейса; для PWA — реальные медленная сеть, повтор входа, обрыв загрузки и устройства. Рабочие базы клиники, реальные телефоны, сеть Black Hole и полный пакет PDF в этом обзоре не измерялись.

## Замеры и методика

Windows x64, AMD Ryzen 5 5600X, Node.js **24.19.0**. Это локальный стенд; CI использует Node.js 22, поэтому цифры не являются гарантией для релизного Electron или сервера. В VM загружены текущие четыре renderer-исходника с заглушками DOM, без отрисовки. SQLite — настоящий `DatabaseService`, отдельные синтетические файлы в `tmp/`.

Два набора: 10 врачей × 12 месяцев; на врача-месяц 50 позиций выработки, по 250 или 1000 пациентских строк в каждом окне 1/12/36. Идентификаторы синтетические, разные у разных врачей. Холодный расчёт всех 120 пар врач–месяц и построение мобильных отчётов измерены по одному разу; короткие операции — три раза. Мобильный экспорт выполнялся после заполнения кэша. Не измерялись IPC, DOM, сетевое время и пиковая память.

## Порядок улучшений

1. **Достоверность:** атомарный импорт; одинаковая совокупность врачей для отношений; полнота мобильной оценки; календарная динамика. Добавить регрессии до изменения поведения.
2. **Быстродействие без переписывания продукта:** точечные сохранения, кэш исходных агрегатов и отделений, детали по запросу; измерить время и память до/после на одном наборе.
3. **Разделение модулей:** извлечь расчёты с явными входами `data + profile + period`, единый числовой `ReportModel` с полнотой, источниками и версией методики; сохранить адаптер старого глобального API.
4. **Фоновые задачи:** перенести импорт, запись и сборку публикаций в ограниченные очереди workers; единая ревизия данных на отчёт, прогресс и отмена.
5. **Мобильное развитие:** сначала паритет готовых отчётов и устойчивость сети; затем, если нужен мобильный Admin, серверные команды и задачи импорта. Совместимость SQLite и старых пакетов проверять на каждом этапе.

Модульная цель: `источники → нормализованные данные → расчётное ядро → ReportModel → Admin / Viewer / PWA / PDF`. SQLite остаётся владельцем сохранённых данных, UI — владельцем только состояния экрана. Микросервисы и полная смена фреймворка для этих исправлений не требуются.
