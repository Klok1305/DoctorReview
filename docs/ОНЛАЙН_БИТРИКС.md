# Онлайн-КлинВект в Битриксе

Admin 3.1.2 выгружает обезличенный JSON с доступом по ФИО и существующему PIN Viewer. В файле — показатели, таблицы и числовые серии графиков; HTML и картинки при выгрузке не создаются. Администратор вручную загружает его в приложение Битрикса. ID сотрудников и ключ API вводить не нужно.

## Выгрузка и загрузка

1. В Admin откройте «Настройки → PIN врачей и публикация в Viewer». Проверьте существующие четырёхзначные PIN; при необходимости выгрузите все PIN в Excel. Задайте администраторский PIN Viewer (6–12 цифр), если он ещё не настроен.
2. Откройте «Настройки → Онлайн-КлинВект в Битрикс24». В таблице также видны ФИО и сохранённые PIN врачей. Как в полной HTML-выгрузке, онлайн-JSON использует существующие PIN всех врачей, независимо от флажка обычной ZIP-публикации.
3. Заведующие отделений берутся из сохранённых назначений Viewer. Для заведующего специализацией включите флажок напротив его врача; область соответствует его специализации в структуре Admin.
4. Нажмите «Выгрузить обезличенный JSON» и сразу выберите папку и имя файла. Затем начнётся подготовка личных отчётов, сводок специализаций, отделений и клиники за все рассчитанные месяцы с «Выработкой». Окно показывает выбранный путь и количество подготовленных отчётов; после завершения путь остаётся в настройках. JSON сохраняется атомарно: незавершённый файл не заменяет прежний. Графики строятся из чисел при открытии отчёта онлайн. Пропуски, пояснения неполных оценок и текущие комментарии сохраняются.
5. Откройте приложение из Битрикс24, раскройте «Загрузить обезличенный JSON», выберите файл и нажмите «Загрузить отчёты». Первый файл загружает администратор портала. Затем загрузка доступна администратору портала или вошедшему с PIN администратору КлинВекта.
6. Выберите ФИО и введите существующий PIN. Администратор выбирает «Администратор» и вводит PIN Viewer. После замены JSON нужно войти снова; новые отчёты, роли и изменения PIN передаются следующей выгрузкой.

Используйте именно кнопку «Выгрузить обезличенный JSON». Полная JSON-копия на вкладке «Данные» содержит рабочую базу и сервером отвергается.

Имена врачей остаются. ФИО, ID и отдельные строки пациентов, реестр, исходные XLS/Excel и рабочие месяцы базы в пакет не входят. Открытых PIN в файле нет: передаются существующие хеши scrypt с солью и фиксированными параметрами проверки. Проверка известных имён и непрозрачных идентификаторов пациентов выполняется в worker за один проход по тексту. Врач, который также есть в пациентской базе, допускается в явно обозначенном столбце «Врач»; совпадение в свободном комментарии по-прежнему останавливает экспорт. Комментарии должны оставаться без данных пациентов.

## Доступ

Приложение открывается через свою учётную запись Битрикса. Внутри КлинВекта пользователь выбирает ФИО и вводит обычный PIN из HTML-выгрузки. Сессия привязывается к текущему сотруднику и порталу; вручную указывать ID не требуется.

| Роль | Доступ |
|---|---|
| Врач | Только собственные личные отчёты |
| Заведующий специализацией | Сводка своей специализации и собственные отчёты |
| Заведующий отделением | Отделение, его специализации, все врачи отделения и собственные отчёты |
| Администратор КлинВекта | Все страницы клиники со всеми опубликованными комментариями |

Роли складываются. Заведующий без личной «Выработки» сохраняет доступ к управляемой области. Администратор портала может загрузить файл, но для просмотра всех показателей ему также нужен администраторский PIN Viewer. Каждый новый JSON содержит ровно одну администраторскую учётную запись с проверочным хешем PIN.

После пяти неверных PIN вход для текущего сотрудника блокируется на 15 минут; смена ФИО не обходит ограничение. Сессия действует до 12 часов. HttpOnly-cookie дополняется отдельным клиническим токеном только в памяти страницы: он позволяет работать внутри iframe, когда Safari блокирует сторонние cookie. Токен передаётся заголовком, не сохраняется в URL, localStorage или sessionStorage; gateway-ключи и сессии Битрикса в браузер не выдаются. HTML отчёта загружается после серверной проверки и открывается через `srcdoc`. При блокировке cookie после перезагрузки нужно вновь ввести PIN, как в HTML-выгрузке. Обновление публикации, выход и перезапуск сервера отзывают сессии. scrypt выполняется асинхронно, максимум два вычисления одновременно; активные сессии сохраняются при достижении лимита 2000.

Сервер проверяет права на каждую страницу и каждую порцию загрузки. Адрес чужого отчёта не открывает доступ. Пользователю выдаётся только разрешённый каталог.

## Открытие с телефона

Онлайн-отчёты имеют адаптивную раскладку: карточки на узком экране идут в один столбец, длинные таблицы прокручиваются внутри своего блока, графики строятся в SVG. Отдельную выгрузку для телефона делать не требуется.

У существующей карточки Битрикса API возвращает `mobile: false` (проверено 2026-10-08). Для появления приложения в мобильном меню администратор портала должен один раз на компьютере открыть «Приложения → Разработчикам → Интеграции → КлинВект», выбрать «Редактировать» и включить «Поддерживает Битрикс24.Мобильный». После сохранения перезапустите Битрикс24 на телефоне и найдите КлинВект в меню. Обновление серверного кода само по себе этот флажок карточки не меняет. [Официальная документация](https://apidocs.bitrix24.ru/local-integrations/static-local-app.html).

## Сервер

Действующее приложение: [КлинВект](https://app-3626f5d534ce.vibecode.bitrix24.tech). **2026-10-08** пакет **3.1.2** с числовым JSON v3 установлен на прежний сервер `96e03bfd-5995-4ac7-b8ba-7b6734bd1469`, исходники Вайбкода **v5**, операция `cmuzocfln392z4bpgaegef1fo`. Служба работает от `vibeapp`; 23 файла пакета и четыре HTTPS-ресурса совпали с исходниками. Краткосрочный проверочный токен отозван (HTTP 401). Клиническая публикация на сервере отсутствует; пользователь загружает её из исправленного Admin. Прежний неисправный сервер пользователь удалил.

На этой VM установлен официальный Node.js **22.23.3**, SHA-256 архива проверен. Текущая команда сервиса — `/opt/klinvekt-node/node-v22.23.3-linux-x64/bin/node /opt/app/server.cjs`; Node отсутствует в стандартном PATH. Для следующего деплоя сохраните эту команду либо предварительно проверьте актуальный установленный рантайм. Проверка работоспособности — корень `/` (HTTP 200), отдельного `/health` у приложения нет. Сервис работает от `vibeapp`, данные — в `/opt/klinvekt-data`, код — в `/opt/app`. Доступ `PORTAL`, прежнее автоусыпление после 60 минут сохранено. Ключ деплоя приложению не нужен: оно использует удостоверенные заголовки gateway, не обращаясь к API Битрикса.

Серверный каталог 3.1.2 собирается командой `pnpm run build:mobile-server`; для ручного размещения используйте его содержимое. Опубликованный пакет 3.1.1 читает прежние v1/v2-файлы. Разверните актуальный пакет на существующем сервере Вайбкода с Node.js ≥22, портом 3000 и командой `node server.cjs`. Сохраните прежнюю политику доступа `PORTAL`/`NAMED_USERS` и непубличный gateway. Укажите:

```text
KLINVEKT_CLOUD_PORTAL_ID=<внутренний UUID портала из gateway>
KLINVEKT_DATA_DIR=/opt/klinvekt-data
```

ID портала — внутренний UUID из `X-Vibe-Portal-Id`, а не домен. Заголовки доверяются только за защищённым gateway Вайбкода. Настроенный онлайн-режим открывается по `/` и `/mobile/`, даже до первой публикации. Прежняя PWA с PIN остаётся по `/mobile/index.html`.

Каталог данных должен сохраняться при обновлении и быть доступен сервисному пользователю на запись. Текущая публикация хранится в `publications.kvcloud` вместе с ID портала. Прежний `.kvmobilebundle` остаётся отдельным файлом. Не помещайте данные в публичную папку или Git.

Официальный контракт: [gateway и контекст пользователя](https://vibecode.bitrix24.tech/docs/infra/app-runtime).

## Проверка файла и сбои

Формат `klinvekt-cloud-publication` v3 содержит метаданные врачей, роли, проверочные хеши PIN и структурированные отчёты с SHA-256. Каждый вложенный объект проверяется по списку разрешённых полей; пациентские поля, HTML, открытые PIN, неверные параметры scrypt, области, числовые значения и хеши отвергаются. Сервер создаёт HTML/SVG только для выбранного разрешённого отчёта; числовые данные остальных страниц в каталог не выдаются. Прежние v1 с привязкой к Битриксу и v2 с HTML читаются для совместимости. Предел файла — 100 МиБ, одного отчёта — чуть менее 4 МиБ. Каталог выдаётся порциями по 128 страниц.

Файл передаётся порциями по 512 КиБ с хешами, таймаутами и ограниченными повторами. При обрыве или отмене выберите тот же файл и повторите загрузку: полученные порции доступны 20 минут до перезапуска сервера. Только полностью проверенный файл атомарно заменяет прежние отчёты. Неверный файл или незавершённая загрузка сохраняют действующую публикацию.

Отчёты имеют `Cache-Control: no-store`; сервис-воркер кэширует только оболочку. Offline-просмотр серверных отчётов не реализован.

## Дополнительная отправка через API

В Admin дополнительный свёрнутый блок позволяет сохранить ID приложения и ключ внешнего API. Это отдельный способ, требующий включения External API и разрешённого ID ключа в `KLINVEKT_CLOUD_KEY_IDS` на сервере. Ключ хранится через Windows safeStorage отдельно от базы. Для ручного сценария этот блок заполнять не требуется.

## Проверки

Node-тесты проверяют восстановление постоянных PIN, форматы v1/v2/v3, числовое совпадение с Admin, пропущенный месяц, отсутствие обращения к DOM/canvas при экспорте, проверку персональных данных, выбор файла до вычислений и атомарное сохранение. Также проверяются роли, межсайтовые запросы, привязка cookie/токена к сотруднику, неверный PIN и блокировка, лимит сессий, повторные порции и отзыв доступа после замены/перезапуска. Electron smoke проверяет видимые PIN в Admin, числовой JSON, агрегаты, комментарии и отсутствие реестра. WebKit проверяет вход по ФИО/PIN, ведущие нули, выход, узкий и горизонтальный экран iPhone, ручную загрузку v3, точные серии графика и отказ полной копии базы. Отдельный HTTPS-сценарий моделирует разные origin Битрикса и приложения с заблокированными cookie: вход, личный отчёт и выход работают, токен не сохраняется на устройстве или в адресе.

После подключения нужно проверить вход настоящими учётными записями врача, заведующих и администратора. Локальные тесты эмулируют gateway и не подтверждают настройку живого портала или работу на физических телефонах.
