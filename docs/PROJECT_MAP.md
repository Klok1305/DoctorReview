# Карта проекта «КлинВект Щербатова»

> Обязательный навигационный контекст для новых задач. Код — источник истины; если архитектура изменилась, обновите эту карту по правилам из корневого `AGENTS.md`.

- Последняя проверка карты: **2026-09-01**.
- Текущая версия при проверке: **2.6.0**. Авторитетное значение находится в `package.json`.
- Репозиторий: `Klok1305/DoctorReview`.
- Платформа: Windows, Electron 37, Node.js 22, pnpm 11.
- Продукты: локальное приложение **Admin**, отдельный **Viewer** без доступа к рабочей SQLite и мобильная **PWA + Node.js-сервер для Bitrix24 Black Hole**; статический демо-режим PWA сохранён для локальной проверки.

## Система в одном абзаце

Admin загружает локальные выгрузки 1С (`.xls`, `.xlsx`, `.zip`), распознаёт и нормализует их в renderer, сохраняет единый снимок состояния и служебные сущности в SQLite, рассчитывает метрики врачей/специализаций/отделений и формирует PDF, Excel и зашифрованные публикации Viewer. Установленный Viewer импортирует проверяемый ZIP в отдельное файловое хранилище; автономный Viewer является одним HTML с встроенными ресурсами и зашифрованными данными. Врач входит по постоянному четырёхзначному PIN и видит только разрешённые страницы; назначенный заведующий также видит врачей своего отделения, а администратор автономного HTML — полный каталог включённых в файл отчётов.

Мобильная PWA не читает SQLite или Viewer-публикации. Для локального пилота она по-прежнему принимает незашифрованный `.kvmobile` одного врача только в память страницы. Рабочий поток 2.6 использует один `.kvmobilebundle`: Admin собирает отчёты всех активных врачей, desktop повторно валидирует их и шифрует каждый отчёт существующим четырёхзначным PIN Viewer. Node.js-сервер Black Hole принимает пакет только от администратора портала, хранит его зашифрованным, проверяет учётную запись Битрикс24 по gateway-заголовкам, ограничивает попытки PIN и выдаёт расшифрованный личный отчёт только в HttpOnly-сессию врача.

## Архитектурный маршрут

```text
Выгрузки 1С
  → desktop/services/file-service.cjs (безопасное чтение локальных файлов)
  → build/app-parsers.js (определение типа и нормализация)
  → build/app-core.js (DB: состояние, миграции, профили и настройки)
  → build/app-metrics.js (расчёты и динамика)
  → build/app-ui.js + build/app.css (Admin UI и подготовка отчётов)
  → window.desktopAPI / desktop/preload.cjs
  → desktop/main.cjs (валидация IPC и оркестрация)
  → desktop/services/database.cjs (SQLite) / экспорт / резервные копии

Публикация Viewer
  → build/app-ui.js: composeViewerDashboardHtml(), exportViewerPackage()
  → desktop/services/viewer-package-service.cjs (санитизация, упаковка, шифрование)
  ├─ ZIP → viewer/storage-service.cjs → установленный Viewer
  └─ один HTML → viewer/standalone.html + viewer/standalone-app.js

Мобильная публикация
  → build/app-ui.js: buildMobilePublication() для одного врача
  ├─ mobile-publication:export → незашифрованный .kvmobile для локального пилота
  └─ exportAllMobilePublications() → mobile-publication:export-bundle
      → database.viewerExportCredentials() → существующие PIN активных врачей
      → desktop/services/mobile-publication-service.cjs
      → один .kvmobilebundle, AES-256-GCM + scrypt отдельно для каждого врача
      → mobile-server/server.cjs на Bitrix24 Black Hole
         ├─ gateway-учётная запись и роль Битрикс24
         ├─ администратор загружает общий пакет
         └─ врач выбирает имя и вводит PIN → личная HttpOnly-сессия
  → mobile-pilot/app.js (серверный вход либо локальный импорт .kvmobile)
  ├─ mobile-pilot/demo-data.js (синтетический fallback)
  └─ mobile-pilot/app.css + index.html
  → manifest.webmanifest + service-worker.js → установка PWA и кэш оболочки
```

## Быстрая навигация по исходникам

### Сборка renderer Admin

| Путь | Ответственность |
|---|---|
| `build/index.template.html` | Разметка Admin и placeholders для встроенных ресурсов. |
| `build/app.css` | Общие стили Admin, отчётов, печати и опубликованных страниц Viewer. |
| `build/app-core.js` | Глобальное состояние `DB`, версия его формата `APP_VERSION`, миграция `migrateDB()`, профили отделений, справочники и сохранение. |
| `build/app-parsers.js` | `detectReportType()` и парсеры отчётов 1С: выработка, назначения, клиентская база, первичка и другие входные форматы. |
| `build/app-metrics.js` | `computeMetrics()`, `computeMetricsRaw()`, динамика врача и агрегаты отделения. Чистая расчётная логика должна жить здесь. |
| `build/app-ui.js` | Состояние `UI`, все экраны Admin, настройки, комментарии, PDF/Excel, композиция публикаций Viewer и `buildMobilePublication()` для агрегированной мобильной выгрузки. Старт — `initApp()`. |
| `build/assemble.ps1` | Встраивает CSS, vendored-библиотеки и четыре JS-модуля в корневой `index.html`. |
| `index.html` | Отслеживаемый **сгенерированный** результат. Не редактировать вручную. |

Renderer не использует bundler и ES-модули: `app-core.js`, `app-parsers.js`, `app-metrics.js` и `app-ui.js` выполняются в общем глобальном контексте в указанном порядке. Библиотеки XLSX, JSZip, Chart.js, html2canvas и jsPDF хранятся локально в `build/*.min.js`; сетевой runtime не требуется.

### Electron Admin и локальные сервисы

| Путь | Ответственность / поисковые якоря |
|---|---|
| `desktop/main.cjs` | Главная точка входа Admin, создание `BrowserWindow`, инициализация сервисов, IPC `registerIpc()`, прямой Chromium-рендер PDF `renderHtmlToPdf()`, smoke/PDF-smoke сценарии. |
| `desktop/preload.cjs` | Единственный renderer-мост `window.desktopAPI`; список разрешённых IPC-вызовов. |
| `desktop/services/config-store.cjs` | Рабочая папка и `config.json`; структура каталогов, миграция прежних путей, запрет OneDrive/UNC/SMB. |
| `desktop/services/database.cjs` | SQLite, миграции, снимок `DB`, импорты/экспорты, комментарии, публикации, PIN Viewer, заведующие и аудит. Класс `DatabaseService`. |
| `desktop/services/file-service.cjs` | Чтение входных файлов только из разрешённых путей, журналирование импортов и атомарная пакетная запись результатов. |
| `desktop/services/backup-service.cjs` | Проверка SQLite, автоматические/ручные `.ovbackup`, восстановление со страховочной копией и очистка старых копий. |
| `desktop/services/update-service.cjs` | Проверка GitHub Releases, загрузка/установка обновления Admin после обязательной резервной копии. |
| `desktop/services/viewer-package-service.cjs` | Общая реализация форматов Viewer: HTML-санитизация, ZIP, автономный HTML, AES-256-GCM, scrypt/PBKDF2 и проверка целостности. |
| `desktop/services/mobile-publication-service.cjs` | Схемы `.kvmobile` и `.kvmobilebundle`, ограничение размера, рекурсивный запрет пациентских/сырых полей, отдельное AES-256-GCM+scrypt шифрование и расшифровка публикации каждого врача. |

`desktop/main.cjs` обязан валидировать недоверенные IPC-параметры до передачи сервисам. Renderer работает с `contextIsolation: true`; Node API напрямую ему не доступен.

### Мобильная PWA и сервер Black Hole

| Путь | Ответственность |
|---|---|
| `mobile-pilot/index.html`, `app.css`, `app.js` | Мобильный интерфейс: серверный выбор врача и PIN, административная загрузка `.kvmobilebundle`, локальный fallback `.kvmobile`, KPI, В1–В6, периоды, динамика, цели и установка PWA. Персональный список пациентов намеренно исключён. |
| `mobile-pilot/demo-data.js` | Только синтетические показатели тестового врача, включая агрегированные окна клиентской базы 12/24/36 месяцев; рабочие выгрузки и реестр пациентов сюда добавлять нельзя. |
| `mobile-pilot/manifest.webmanifest`, `service-worker.js`, `icons/*` | Метаданные установки и локальный кэш статической оболочки. |
| `scripts/serve-mobile-pilot.cjs` | Локальная раздача каталога без внешних зависимостей; режим `--lan` нужен только для проверки интерфейса в локальной сети. |
| `mobile-server/server.cjs` | Node.js HTTP-сервер Black Hole на порту 3000: gateway identity, проверка роли администратора, хранение общего зашифрованного пакета, rate limit PIN, HttpOnly-сессии и API личного отчёта. |
| `scripts/build-mobile-server-package.cjs` | Собирает автономный деплой-каталог `tmp/klinvekt-mobile-server` с сервером, общим сервисом формата и PWA; GitHub Release упаковывает его в ZIP. |
| `docs/МОБИЛЬНЫЙ_ПИЛОТ.md` | Развёртывание Black Hole, общий экспорт из Admin, обновление всех врачей, вход по PIN, локальная проверка и границы безопасности. |

Мобильный сервер не входит в NSIS-установщики, но публикуется отдельным ZIP в GitHub Release. Рабочий пакет `.kvmobilebundle` не входит в релиз и Git: его создаёт клиника локально после импорта выгрузок. Black Hole должен иметь политику доступа `PORTAL`, а не `PUBLIC`; сервер дополнительно отклоняет API-запросы без `X-Vibe-User-Id`.

Viewer не открывает рабочую SQLite Admin. ZIP хранит каталог и зашифрованные страницы в отдельной папке Viewer. Автономный HTML формата 3 не требует установки и содержит независимые зашифрованные payload: персональные наборы для врачей/заведующих и полный каталог для администратора. При экспорте администраторский PIN проверяется по хэшу SQLite, используется только в памяти и не записывается открытым текстом. Старые автономные HTML формата 2 остаются самодостаточными и продолжают открываться своей встроенной оболочкой. Для заведующего навигация строится из уже разрешённых ему страниц: отдельно доступны личный отчёт выбранного врача, общий отчёт каждого управляемого отделения и все опубликованные специализации этого отделения. Список специализаций выводится из структуры `subjects`, а не задаётся в коде вручную. На личной странице безопасные обработчики оболочки Viewer переключают заранее сформированные окна назначений Вектора 3 и клиентской базы 12/24/36 месяцев; пациентский реестр сворачивается, а рейтинг каждой площадки выводится только для чтения. Исполняемый код в опубликованный отчёт не добавляется.

## Данные, хранение и безопасность

### Рабочая папка Admin

`ConfigStore` создаёт на локальном диске:

```text
<рабочая папка>
├─ Входящие
├─ База/оценка-врачей.sqlite
├─ Результаты
├─ Резервные копии
└─ Журналы
```

Путь хранится в `%APPDATA%/.../config.json`. Существуют миграции со старых имён приложения. OneDrive и сетевые UNC/SMB-пути намеренно отклоняются из-за риска повреждения SQLite.

### SQLite

Миграции определены только в `desktop/services/database.cjs` и фиксируются в `schema_migrations`. Основные группы таблиц:

- снимок и справочники: `app_settings`, `app_meta`, `doctors`, `months`;
- происхождение данных: `source_files`, `import_batches`, `import_events`, `export_runs`;
- комментарии и история: `comments`, `comment_versions`;
- публикации: `publications`, `published_pages`, `viewer_exports`;
- доступ Viewer: `viewer_settings`, `viewer_doctor_access`, `viewer_department_heads`;
- совместимость/аудит: `users`, `audit_log`.

Изменение схемы требует новой идемпотентной миграции и теста в `tests/database.test.cjs`. Не переписывайте существующую миграцию, уже попавшую в релиз.

### Полная переносимая JSON-копия

Кнопка «Полная копия в JSON» в настольном Admin создаёт версионированный контейнер `klinvekt-portable-json`, а не только renderer-снимок `DB`. `DatabaseService.createPortableJson()` берёт авторитетные данные непосредственно из SQLite и включает:

- основной снимок аналитики, структуры врачей и настроек;
- источники и историю импортов/экспортов;
- пользователей, комментарии и всю историю версий комментариев;
- публикации и сохранённые страницы;
- журнал аудита;
- настройки Viewer, активность и PIN врачей, администраторский PIN-хэш, историю Viewer-экспортов и фактических заведующих из `viewer_department_heads`.

При создании копии `snapshot.settings.departmentHeadDoctorIds` принудительно синхронизируется с фактической SQLite-таблицей заведующих: старое или предустановленное значение renderer не должно заменять реальное назначение. `DatabaseService.restorePortableJson()` восстанавливает основной снимок и служебные таблицы; IPC `database:import-json` предварительно создаёт страховочную SQLite-копию и автоматически откатывается к ней при ошибке. Старые JSON без контейнера по-прежнему импортируются как аналитический снимок без отсутствовавших в них комментариев и доступов.

Полный JSON содержит персональные данные и действующие PIN Viewer. Его нельзя добавлять в Git или хранить в незащищённой/облачной папке. Для побайтовой копии SQLite и штатного аварийного восстановления предпочтителен `.ovbackup`.

### Границы доступа

- Admin не показывает экран логина: доверенной границей является локальная учётная запись Windows и доступ к рабочей папке.
- PIN врача — ровно 4 цифры. Он защищает его payload/страницы Viewer.
- Admin PIN Viewer — 6–12 цифр. Он управляет импортом ZIP, административным режимом установленного Viewer и расшифровывает полный каталог автономного HTML.
- Отчёты шифруются AES-256-GCM, ключ выводится через scrypt; метаданные и хэши проверяются до показа.
- Отчёты заведующего формируются как набор разрешённых страниц врачей назначенного отделения.
- Переключатель заведующего «личный отчёт / всё отделение / специализации» не расширяет доступ: каждая кнопка выбирает одну из уже зашифрованных страниц разрешённого `subjectDoctorId`; отсутствующие в публикации типы страниц не показываются.
- Реестр пациентов существует только на личных страницах врачей, находится внутри PIN-зашифрованного содержимого и не должен появляться в открытой оболочке автономного HTML, страницах отделений или специализаций. Для каждого доступного окна клиентской базы он явно показывает месяц отчёта, период исходной выгрузки и длительность анализа; отсутствующие точные окна не заменяются данными другого периода.
- `sanitizeReportHtml()` удаляет исполняемые/опасные элементы перед публикацией. Не ослабляйте санитизацию без отдельной модели угроз и тестов.
- Встроенный набор PWA публично безопасен и содержит только синтетические данные. Локальный `.kvmobile` одного врача не зашифрован и не должен попадать в публичные каталоги или общие чаты. Рабочий `.kvmobilebundle` шифрует отчёты отдельно по PIN, но из-за четырёхзначного PIN также передаётся только администратору Black Hole и никогда не раздаётся врачам как файл.
- Black Hole gateway является первой границей доступа и передаёт идентификатор/роль пользователя серверу. Серверная роль разрешает загрузку пакета только администратору, PIN блокируется после пяти неверных попыток, а обновление пакета завершает старые мобильные сессии.

## Основные пользовательские потоки

### Импорт

1. `FileService` выбирает/читает локальный файл и вычисляет происхождение.
2. `app-parsers.js` распознаёт структуру листа, возвращает нормализованные записи.
3. Renderer обновляет `DB`; `app-core.js` мигрирует старые снимки.
4. `desktopAPI.database:save` сохраняет снимок в SQLite; импорт фиксируется отдельным batch/event.

При добавлении формата меняйте детектор, конкретный parser, фикстуры/тесты и описание поддерживаемых форматов. Не привязывайте расчёты к сырым заголовкам Excel.

### Расчёты и отчёты

Профили/нормативы берутся из `app-core.js`, расчёты выполняет `app-metrics.js`, визуальное представление строит `app-ui.js`. Общий индекс состоит из шести настраиваемых векторов. Отделение и специализация агрегируют врачей, но не должны дублировать персональные данные пациентов.

### PDF и Excel

- Admin готовит самостоятельную печатную HTML-страницу в `app-ui.js`.
- Desktop передаёт её через `export:render-pdf`; `desktop/main.cjs` печатает скрытым Chromium `BrowserWindow.printToPDF()` в A4 landscape с CSS-разбиением.
- Файлы атомарно пишет `FileService` в `Результаты`.
- Excel формируется локально через встроенный SheetJS (`XLSX`).

Не возвращайте PDF к схеме «огромный canvas/картинка на странице»: это делает длинные блоки нечитаемыми.

### Публикация Viewer

1. `composeViewerDashboardHtml()` клонирует подготовленный отчёт, добавляет комментарии и разрешённые персональные блоки.
2. `exportViewerPackage()` собирает получателей, видимые страницы, периоды и роли.
3. `viewer-package-service.cjs` санитизирует и шифрует содержимое.
4. Результат — проверяемый ZIP для установленного Viewer или один автономный HTML.

После входа обычный врач видит опубликованные для него типы страницы. Заведующий дополнительно получает независимый переключатель сводного отчёта: личный отчёт показывается отдельно, а сводные кнопки сгруппированы строками «отделение / его специализации». Выбор «Врач отделения» остаётся отдельным и относится к личным отчётам врачей. В диалоге публикации личные страницы, специализации и отделения выбраны по умолчанию. Отдельный режим заведующих определяет состав публикации: по умолчанию включаются только явно выбранные врачи и их сводные, а опциональный режим добавляет всех врачей управляемых отделений.

Автономный HTML требует подтверждения текущего Admin PIN во время экспорта. Отдельный администраторский вход показывает все страницы, реально включённые в файл, но не расширяет сам состав выбранных при экспорте периодов и типов отчётов.

При изменении формата сохраняйте чтение старых поддерживаемых пакетов либо явно добавляйте версию формата и миграционный/отказоустойчивый путь.

### Мобильная публикация

1. `buildMobilePublication()` берёт до шести последних периодов врача и переносит KPI, В1–В6, доступные окна, динамику и цели без `clientRows`, имён/ID пациентов и сырых отчётов.
2. Одиночный IPC `mobile-publication:export` сохраняет `.kvmobile` только для локального пилота.
3. Пакетный `exportAllMobilePublications()` собирает публикации всех активных Viewer-врачей с данными; IPC получает их PIN из SQLite и создаёт один `.kvmobilebundle` с отдельным шифрованием каждого payload.
4. Администратор Битрикс24 загружает пакет серверу. API никогда не отдаёт пакет клиенту: публично возвращается только список врачей, после правильного PIN — расшифрованный личный отчёт в сессию пользователя.
5. Повторная загрузка общего пакета атомарно заменяет текущую публикацию и отзывает открытые мобильные сессии.

## Тесты и команды

| Команда | Назначение |
|---|---|
| `pnpm install --frozen-lockfile` | Воспроизводимая установка зависимостей. |
| `pnpm run assemble` | Пересобрать отслеживаемый `index.html`. |
| `pnpm run audit:repo` | Проверить белый список Git: без данных клиники, сборок и секретов. |
| `pnpm test` | Все Node-тесты `tests/*.test.cjs`. |
| `pnpm run test:smoke` | Реальный Electron renderer, основные экраны/экспорты и PNG-артефакты в `tmp/`. |
| `pnpm run test:pdf` | Один реальный PDF через Chromium и проверки результата. |
| `pnpm run dist:all` | Локальные NSIS-сборки Admin и Viewer. |
| `pnpm run start:mobile-pilot` | Локально открыть PWA на `http://127.0.0.1:4173/`. |
| `pnpm run start:mobile-pilot:lan` | Показать интерфейс на телефоне в той же локальной сети; для установки PWA всё равно нужен HTTPS. |
| `pnpm run start:mobile-server:local` | Локально открыть серверный сценарий на `http://127.0.0.1:3000/mobile/` с тестовой ролью администратора. |
| `pnpm run build:mobile-server` | Собрать автономное содержимое для деплоя Black Hole в `tmp/klinvekt-mobile-server/`. |

Тестовые файлы разделены по назначению:

- `tests/legacy-core.test.cjs` — legacy/global renderer, парсеры, расчёты и построение мобильной публикации из метрик;
- `tests/build.test.cjs` — состав сборки и статические инварианты UI;
- `tests/database.test.cjs` — миграции и SQLite;
- `tests/desktop-services.test.cjs` — конфигурация, файлы, backup/update;
- `tests/auth-publication.test.cjs` — доступ, комментарии и публикации;
- `tests/viewer-publication.test.cjs` — ZIP/HTML Viewer, шифрование и приватность.
- `tests/mobile-pilot.test.cjs` — состав PWA, схемы `.kvmobile`/`.kvmobilebundle`, шифрование по PIN, запрет пациентских полей и отсутствие внешних runtime-ресурсов;
- `tests/mobile-server.test.cjs` — gateway-учётная запись, роль администратора, загрузка пакета, PIN-вход, привязка сессии к пользователю и rate limit.

После изменения `build/*` обычно нужны `pnpm run assemble`, `pnpm test` и соответствующий smoke. После изменения только документации достаточно `pnpm run audit:repo` и проверки ссылок/карты.

## CI, релиз и артефакты

- `.github/workflows/ci.yml`: на `main` и PR — frozen install, audit, Node-тесты.
- `.github/workflows/release.yml`: тег `v*.*.*`, проверка тега против `package.json`, audit, тесты, `dist:all`, затем атомарная публикация GitHub Release.
- Admin собирается по корневому `package.json`; Viewer — по `electron-builder.viewer.json`.
- Релиз содержит: Admin Setup EXE, его `.blockmap`, `latest.yml`, Viewer Setup EXE и автономный `KlinVekt-Mobile-Server-<version>.zip` без рабочих данных.
- Автообновление используется только Admin. Viewer обновляется отдельным установщиком.
- `dist/`, `tmp/`, `output/`, пользовательские документы и рабочие базы — артефакты, не исходники и не Git-контекст.

Релизные инструкции и совместимость версий подробно описаны в `docs/ОБНОВЛЕНИЕ.md`; пользовательская эксплуатация — в `README.md` и `docs/ИНСТРУКЦИЯ.md`.

## Как поддерживать эту карту

При значимом изменении:

1. Исправьте существующий раздел вместо добавления хронологической заметки.
2. Добавьте новый файл в таблицу навигации и матрицу изменений, если без него будущий агент не найдёт владельца логики.
3. Обновите поток данных и границы безопасности, если они поменялись.
4. Обновите дату проверки; версию — только одновременно с `package.json`.
5. Проверьте упомянутые пути через `git ls-files` и запустите `pnpm run audit:repo`.
