Эти инструкции действуют для всего репозитория.

## Самое важное при релизе

После успешного push нового тега **сразу сообщи «Релиз <version> запущен» и всегда дай [ссылку на страницу релизов](https://github.com/Klok1305/DoctorReview/releases)**. Не жди завершения GitHub Actions, сборки установщиков или публикации файлов. Не запускай мониторинг без отдельной просьбы. При ошибке push сообщи ошибку и ту же ссылку, не объявляя релиз запущенным. Подробный порядок подготовки — в разделе «Запуск релиза» ниже.

## Начало каждой задачи

1. Сначала полностью прочитай [`docs/PROJECT_MAP.md`](docs/PROJECT_MAP.md).
2. Используй карту как индекс: открывай только файлы, относящиеся к задаче, и связанные тесты. Не начинай с полного обхода репозитория, `node_modules`, `dist`, `tmp`, `output` или с чтения сгенерированного `index.html`.
3. Перед изменением всё равно проверь актуальный код в перечисленных картой файлах. Карта ускоряет навигацию, но код остаётся источником истины.
4. Если карта расходится с кодом, исправь карту в той же задаче.

## Обязательное сопровождение карты

Обновляй `docs/PROJECT_MAP.md` в той же задаче, если изменение затрагивает хотя бы один из пунктов:

- добавлен, удалён или переименован модуль, сервис, точка входа либо основной каталог;
- изменились владельцы логики, поток данных или связь Admin → IPC → сервисы → SQLite;
- изменились схема/миграции SQLite, формат снимка состояния, импорта, резервной копии, PDF, Viewer ZIP или автономного HTML;
- изменились права доступа, PIN, шифрование, обработка персональных данных или границы между Admin и Viewer;
- изменились сборка, генерация `index.html`, команды проверки, CI, релизный процесс или состав установщиков;
- появилась крупная пользовательская подсистема, для которой будущему агенту нужна новая точка навигации.

Не превращай карту в changelog. Локальный рефакторинг или исправление внутри уже описанной подсистемы не требует записи, если утверждения и маршруты карты остались верны. При обновлении карты меняй дату проверки; номер версии бери только из `package.json`.

## Неподвижные правила разработки

- `index.html` генерируется из `build/index.template.html`, `build/app.css` и `build/app-*.js` командой `pnpm run assemble`. Не исправляй его вручную; после правок исходников пересобери и включи обновлённый `index.html` в изменение.
- Не добавляй в Git данные клиники, выгрузки, базы, резервные копии, отчёты, установщики или секреты. После изменения состава исходников обнови одновременно `.gitignore` и `scripts/audit-repository.ps1`, затем запусти `pnpm run audit:repo`.
- Для изменений SQLite, Viewer, экспорта и доступа считай совместимость старых рабочих баз и уже выпущенных пакетов обязательной, пока пользователь явно не разрешил разрыв.
- Минимальная проверка кода — `pnpm test`; для UI/рендеринга используй `pnpm run test:smoke`, для PDF — `pnpm run test:pdf`. Полная релизная последовательность описана в карте.

## Запуск релиза

- По просьбе выпустить релиз подготовь проверенные изменения, обнови версию в `package.json`, карту и релизную документацию. Закоммить изменения и отправь `main` вместе с новым тегом `v<version>` через `git push --atomic origin main v<version>`.
- После успешной отправки тега сразу сообщи «Релиз <version> запущен» и дай ссылку https://github.com/Klok1305/DoctorReview/releases. Не жди завершения GitHub Actions, сборки установщиков или публикации артефактов. Не запускай мониторинг без отдельной просьбы.
- Успешный push означает запуск, а не готовность релиза. Если push не удался, сообщи об ошибке вместо заявления о запуске и всё равно дай ссылку на страницу релизов. Действующие теги и опубликованные релизы не перезаписывай.
- Проверки изменённого кода выполняются до push; уже успешно выполненные проверки не повторяй без новых изменений или выявленных проблем.
